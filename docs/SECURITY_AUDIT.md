# Security & Data Isolation Audit

This document certifies that the EduPortal multi-tenant SaaS architecture complies with all security, multi-tenancy isolation, and privacy mandates outlined in **Section 4** of the Master Specification.

---

## 1. Multi-Tenant Data Isolation (Section 4.2)

### RLS & Private Schema Helper Functions
- All tenant tables possess `tenant_id uuid not null references tenants(id)` with explicit foreign key indexing.
- Row-Level Security (RLS) is enabled and enforced across all tables in PostgreSQL.
- Tenant context resolution resides strictly within the `private` schema with `security definer` privileges:
  - `private.current_tenant_id()`
  - `private.current_role()`
  - `private.is_platform_owner()`
  - `private.has_feature(feature_key)`
- **Zero Client Trust:** The application layer never trusts client-supplied `tenant_id` parameters. Instead, `tenant_id` is automatically set by database defaults or server-side session headers.
- **Anon Restrictions:** Anonymous `SELECT` queries are permitted only on rows where `is_published = true` for active tenants. Tables containing sensitive personal or financial information (`students`, `guardians`, `invoices`, `payments`, `applications`, `student_documents`, `audit_logs`) completely deny anonymous access.
- **Verification Tests:** Verified via `supabase/tests/rls_test.sql` proving that Tenant A queries can never read or mutate records belonging to Tenant B.

## 2. Authentication, Roles & Permissions (Section 4.3)

### Role Matrix & Least Privilege
The system enforces strict role-based access control across 8 designated platform tiers:
1. `platform_owner`: Global SaaS administrator (us). Tenant ID is null.
2. `school_super_admin`: School Principal / Management with administrative authority over settings, user invitations, and modules.
3. `school_admin`: Day-to-day administrative manager.
4. `data_entry_operator`: Data entry staff. **Explicitly restricted from deleting student records or modifying fee structures.**
5. `accountant`: Financial operator authorized for offline fee collection and receipt generation.
6. `teacher`: Read-only access to academic student rosters.
7. `parent`: Parent PWA portal access to view their linked children, fee invoices, and receipts.
8. `student`: Student PWA portal access to notices and academic calendar.

## 3. Secret Isolation & Zero Client Leakage

- Public environment variables (`NEXT_PUBLIC_*`) are restricted solely to the public Supabase URL, the anonymous key (which is guarded by RLS), and platform brand identifiers.
- Privileged keys (`SUPABASE_SERVICE_ROLE_KEY`, `RAZORPAY_KEY_SECRET`, `RAZORPAY_WEBHOOK_SECRET`, `CLOUDFLARE_API_TOKEN`, `R2_SECRET_ACCESS_KEY`, `RESEND_API_KEY`) reside exclusively in server environments (`apps/api` Worker bindings and server-only `.env`).
- Next.js client bundles are verified free of any service role tokens or privileged secrets.

---

## 4. Digital Personal Data Protection (DPDP Act 2023 Compliance)

Because the platform processes information belonging to minor school students, the following safeguards are implemented:
- **Parental Consent:** The public admission workflow (`/admission`) enforces an explicit consent checkbox for processing minor student data prior to application submission.
- **Data Minimization:** No unnecessary PII is collected on public inquiry pages.
- **Privacy Attribution in Analytics:** The first-party website analytics tracker (`/api/track` and `TrackerScript.tsx`) collects no cookies and no PII, utilizing hashed session tokens.
- **Right to Erasure & Export:** Soft deletes are implemented on sensitive student and fee records, preserving financial audit trails while supporting institutional data deletion and export requests.

---

## 5. File Upload & Storage Security

- Client-side pre-processing automatically validates file MIME types, limits file size, and compresses public images into optimized WebP formats prior to upload (`apps/web/src/lib/storage.ts`).
- Secure cloud uploads are transacted using short-lived signed URLs generated by the privileged Cloudflare Worker (`/api/storage/sign-url`).
- Tenant isolation is maintained in Cloudflare R2 bucket paths: `tenants/{tenant_id}/{module}/{uuid}.webp`.
- Private receipts and admission documents are secured in private storage buckets requiring authentication.

---

## 6. Payment Integrity & Idempotency

- All offline and online payment records require unique `idempotency_key` constraints.
- Duplicate webhook payloads from payment gateways are safely identified and deduplicated, preventing double-invoicing or duplicate receipt generation.
- Sequential, race-safe receipt numbering format: `RCP-YYYY-XXXXX`.
